Step 2 - POINT_EXP chain

Authoritative EXP chain
1. Mob death / combat reward enters `CombatSystem.cpp`
   - `GiveExp(...)` computes the reward
   - final write is `to->PointChange(POINT_EXP, iExp, true);`
2. `PointChange(POINT_EXP, ...)` is handled in `PointSystem.cpp`
   - reads current EXP via `GetExp()`
   - reads next-level threshold via `GetNextExp()`
   - mutates EXP via `SetExp(...)`
3. `GetExp()/SetExp()` are simple wrappers over `m_points.exp` in [char.h](E:/AurigaGlobal/LiveWork/AurigaGlobal/SRC/Server/GameServer/char.h:862)
4. `PointsPacket()` in `NetworkSyncSystem.cpp` serializes:
   - `pack.points[POINT_EXP] = GetExp();`
   - `pack.points[POINT_NEXT_EXP] = GetNextExp();`

Key finding
- Runtime EXP authority is NOT `m_pointsInstant.points[POINT_EXP]`.
- Runtime EXP authority IS `m_points.exp`, reached through `GetExp()/SetExp()` and `PointChange(POINT_EXP, ...)`.
- Therefore any `15C-1j` attempt that turned `GetPoint(POINT_EXP)` into a generic ECS-array lookup (or worse, mapped it directly to current EXP) risks breaking callers that conceptually expect a stat-array field, not the live EXP progression counter.

Step 5 - Root-cause assessment

Most likely regression source
- The failed `15C-1j` attempt likely broke semantic layering, not mechanical mirroring.
- In this codebase, `POINT_*` indices fall into at least three classes:
  1. true instant stat-array values
  2. persistent/base values (`m_points.points[...]`)
  3. live virtual values with dedicated authority:
     - `POINT_EXP` -> `m_points.exp`
     - `POINT_GOLD` -> `m_points.gold`
     - `POINT_HP` / `POINT_MAX_HP` -> health authority
     - `POINT_SP` / `POINT_MAX_SP` -> mana authority
     - `POINT_STAMINA` / `POINT_MAX_STAMINA` -> stamina authority
     - `POINT_LEVEL` -> level getter / base data
- A flat ECS migration that treated all `POINT_*` indices as equivalent array-backed values was therefore semantically unsafe.

Why the metin damage symptom also fits
- Stone damage / break timing depends on multiple live values flowing through `GetPoint()`, `ComputePoints()`, `PointChange()`, and packet sync.
- If helper semantics changed for even a handful of virtual/live points, damage, EXP, and packet-visible state could all desynchronize without any compile error.

Pre-retry fix proposal

Required before any new `15C-1j` retry
1. Keep `CharacterStatsComponent` strictly limited to true stat-array values.
2. Do NOT migrate the following through the generic stats array:
   - `POINT_EXP`
   - `POINT_NEXT_EXP`
   - `POINT_GOLD`
   - `POINT_LEVEL`
   - `POINT_HP`
   - `POINT_MAX_HP`
   - `POINT_SP`
   - `POINT_MAX_SP`
   - `POINT_STAMINA`
   - `POINT_MAX_STAMINA`
3. In `GetPoint()` preserve explicit semantic routing for those indices before any generic array lookup.
4. In `SetPoint()` either:
   - reject virtual/live indices from generic array writes, or
   - route them to their real authority (`SetExp`, gold setter, health/mana/stamina setter, etc.).
5. `GetLimitPoint()` must stop reading raw `m_pointsInstant.points[type]` directly and instead operate on the same semantic view that `GetPoint()` exposes.
6. `PointsPacket()` should continue to source live values from dedicated getters, not from a generic stats array.

New mirror locations needed if retry happens
- Not many distributed call sites.
- The critical mirror/cutover boundaries are the helper bodies themselves:
  - `GetPoint()`
  - `SetPoint()`
  - `GetLimitPoint()`
  - `ComputePoints()`
- If an ECS retry is attempted, the migration must be helper-semantic first, not grep/mirror first.

Retry safety recommendation
- Retrying `15C-1j` immediately as a flat `points[]` move is NOT safe.
- Safe retry requires one pre-work step:
  - split the `POINT_*` universe into:
    - generic stat-array points
    - virtual/live/dedicated-authority points
- After that split, a retry becomes feasible with a narrower component that excludes EXP/gold/vitals/level semantics.

Recommended next move
- Do not retry full `POINT_MAX_NUM` migration yet.
- First implement a semantic allowlist for array-backed points only.
- Then retry only that reduced subset under drift logging.
