# Phase 15C-1: Points Cluster Migration Audit

## Executive Summary
- `CHARACTER_POINT_INSTANT` is structurally dominated by inventory-storage arrays, not by scalar runtime flags.
- The struct is estimated at **34,335 bytes**, matching the `15C-0` estimate.
- The best **first implementation slice** inside the points cluster is **extra inventory storage** (`pExtraItems + wExtraItemGrid`), not the hottest combat fields.
- Reason: it frees **10,800 bytes per CHARACTER** while keeping blast radius localized to ItemSystem feature-gated paths.
- The truly hot fields (`points[]`, `position`, `instant_flag`, `dwAIFlag`, `pItems`, `bItemGrid`) should be migrated later behind mirrored helper boundaries.

## 2. Helper / Indirect Access Amplifiers
These functions hide much of the real heat of the points cluster, so direct field grep counts alone understate risk.
| Helper | Whole-tree hits | Why it matters |
| --- | ---: | --- |
| `GetPoint` | 649 | Main read boundary for `points[]` derived stats. |
| `PointChange` | 417 | Main write boundary for points/vitals recomputation. |
| `GetItem` | 99 | Main read boundary for `pItems` and inventory storage. |
| `GetPart` | 44 | Main read boundary for `parts[]` / appearance. |
| `SetPart` | 44 | Main write boundary for `parts[]` / appearance. |
| `ComputePoints` | 73 | Primary recompute boundary touching multiple fields. |
| `PointsPacket` | 20 | Packet boundary that serializes points-related state. |
| `SetItem` | 14 | Inventory authority write helper. |
| `SetQuickslot` | 11 | Indirect inventory-adjacent UI boundary. |
| `GetQuickslot` | 6 | Indirect inventory-adjacent UI boundary. |

Interpretation:
- `points[]` looks ?cold? in raw field grep (`5` direct refs), but it is actually one of the hottest slices because `GetPoint()` (`649`) and `PointChange()` (`417`) sit on almost every combat/stat/item path.
- `parts[]` also looks light in direct refs, but `GetPart()` / `SetPart()` double the real packet-visible surface.
- `pItems[]` and `bItemGrid[]` are hot even before helper amplification, and their actual fan-out is larger once `GetItem()` and inventory routines are included.

## 4. Migration Order Recommendation
Order is from easiest/lowest-blast-radius toward hottest/highest-risk slices.
- **15C-1a** ? `G_EXTRA_INVENTORY` ? ~10,800 bytes freed. Move `pExtraItems` + `wExtraItemGrid` into `ExtraInventoryRuntimeComponent`. Big byte win (`10,800` bytes) with localized ItemSystem surface.
- **15C-1b** ? `G_CUBE` ? ~200 bytes freed. Extract cube window arrays/pointer. Very low risk transient state slice.
- **15C-1c** ? `G_ATTR_TRANSFER` ? ~32 bytes freed. Extract attr-transfer window items/NPC pointer. Narrow feature surface.
- **15C-1d** ? `G_ACCE` ? ~16 bytes freed. Extract accessory window materials. Tiny but clean isolation.
- **15C-1e** ? `G_SWITCHBOT` ? ~40 bytes freed. Extract switchbot item slots. Small, feature-gated runtime slice.
- **15C-1f** ? `G_DRAGONSOUL` ? ~14,532 bytes freed. Move DragonSoul storage arrays and deck/opener runtime state. Large byte win but dedicated-system coupling.
- **15C-1g** ? `G_APPEARANCE_PARTS` ? ~16 bytes freed. Move `parts[]`/base appearance slice after packet mirroring is proven.
- **15C-1h** ? `G_VITALS_MAX` ? ~24 bytes freed. Move `iMaxHP/iMaxSP/iMaxStamina` once recompute paths are mirrored.
- **15C-1i** ? `G_RUNTIME_FLAGS` ? ~27 bytes freed. Move runtime flags/AI/position bits with careful dual-authority sync.
- **15C-1j** ? `G_INVENTORY_STORAGE + G_COMBAT_STATS` ? ~8,640 bytes freed. Finish the hot main inventory arrays and `points[]` core only after all helper boundaries are mirrored.

**Recommended first substep to implement next: `15C-1a` (`G_EXTRA_INVENTORY`).**
- Expected bytes freed per CHARACTER: **10,800**
- Why first: largest isolated slice with medium/cold access profile and strong feature locality inside ItemSystem.
- Why not `points[]` first: helper fan-out is too large (`GetPoint`, `PointChange`, `ComputePoints`, `PointsPacket`), so a direct first cut would carry far more regression risk.

## 5. Risk Assessment
1. **Dual-authority divergence**
   - Risk: Mirrored ECS data can drift from legacy fields during a long migration window.
   - Mitigation: For every substep, introduce one write-through bridge API first and make all writes flow through it before changing reads.
2. **Hot-path latency / cache regression**
   - Risk: Scattering hot stats and inventory occupancy into too many tiny components can hurt combat and item hot paths.
   - Mitigation: Keep hot slices coarse-grained: one component for extra inventory, one for DragonSoul storage, one for runtime flags, one for combat points.
3. **Packet serialization breakage**
   - Risk: `PointsPacket()` and related UI updates assume immediately coherent point state.
   - Mitigation: Treat `PointsPacket()` as a formal boundary: do not flip authority until the backing component read path is complete and covered by smoke tests.
4. **DB/login initialization ordering**
   - Risk: Load/login code expects the cluster to be fully valid before early packet sends and command handling.
   - Mitigation: Populate ECS mirrors immediately at character creation/login before any packet or command path can read them.
5. **Hidden helper amplification**
   - Risk: Low direct field counts hide huge helper fan-out (`GetPoint`, `GetItem`, `ComputePoints`).
   - Mitigation: Drain helper implementations first; do not rely on raw field grep counts alone when deciding that a field is ?cold?.

## 6. Packet + DB Boundary Scan
Exact raw-layout grep hits (`&m_pointsInstant`, `memcpy(m_pointsInstant)`, `m_pointsInstant[...]`) found: **0**

This is good news: the struct is not being passed around wholesale. The real critical boundaries are helper-based:
- No exact raw `&m_pointsInstant` / `memcpy(m_pointsInstant)` hits ? The layout is not passed around wholesale in current code.
- ecs/systems/PointSystem.cpp:155 `CHARACTER::GetPoint` ? Indirect read boundary for `points[]`.

- input_db.cpp:637, 1805 ? DB/login flow explicitly calls `PointsPacket()` after load/update.

## 7. Concrete Implementation Guidance
Do **not** migrate the points cluster as one giant component. The safer plan is:
1. Start with one isolated storage slice (`G_EXTRA_INVENTORY`).
2. Mirror writes into a new ECS component while legacy fields remain authoritative.
3. Flip read paths in ItemSystem for that slice only.
4. Run item/inventory regressions.
5. Remove the legacy fields for that slice only.
6. Repeat for DragonSoul, then transient windows, then hot runtime flags, and finally `points[]` and main inventory storage.

## 8. Final Recommendation
- **First code implementation target:** `G_EXTRA_INVENTORY`
- **Second:** `G_CUBE` / `G_ATTR_TRANSFER` / `G_ACCE` as low-risk cleanup slices
- **Third:** `G_DRAGONSOUL`
- **Leave for late:** `G_INVENTORY_STORAGE`, `G_RUNTIME_FLAGS`, `G_COMBAT_STATS`
- This ordering maximizes bytes freed early without taking the highest-risk combat/stat authority cuts first.
