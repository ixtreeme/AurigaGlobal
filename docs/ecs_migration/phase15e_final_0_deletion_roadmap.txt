# Phase 15E-final.0 - CHARACTER + CItem Deletion Roadmap Audit

Date: 2026-05-02
Mode: audit and plan only.
Build target: `GameServer` / `RelWithDebInfo`.

## 1. Current State

The project is past accessor migration. The remaining work is subsystem extraction.

Confirmed state:

- CHARACTER read API is pure ECS for migrated gameplay state.
- Accepted E-class service debt remains for `GetDesc` and `GetSectree`.
- Item ECS read API is 100% pure ECS.
- Broad ECS `LPCHARACTER` / `CHARACTER*` surface after Phase 15E-66.2 is 117 matches.
- The remaining 117 are mostly M3 legacy-bound signatures, not safe mechanical signature cleanup.
- `CHARACTER::` method bodies remaining: 751.
- `CItem::` method bodies remaining: 138.

Important topology note:

- The old `char.cpp`, `char_battle.cpp`, `char_item.cpp`, `char_skill.cpp`, `char_state.cpp` and `item.cpp` files are absent.
- Legacy class declarations remain in `char.h` and `item.h`.
- Transitional method bodies now live mostly in ECS subsystem files.

Supporting details:

- Character/class field audit: `docs/ecs_migration/phase15e_final_0_char_class_audit.txt`
- Deletion blocker inventory: `docs/ecs_migration/phase15e_final_0_deletion_blockers.txt`

## 3. CItem Field and Method Audit

| Category | Status | Examples |

Method body hotspots:

| Area | Count | Deletion impact |
|------|------:|-----------------|
| `ItemSystem_LegacyBridge.cpp` | 119 | primary CItem deletion blocker |
| `InventorySystem.cpp` | 15 | inventory/equipment mutation bridge |
| `NetworkSyncSystem.cpp` | 4 | packet bridge |

Conclusion:

Item read access is clean, but CItem deletion is blocked by lifecycle and mutation behavior. The next item phase is not more read fallback work; it is item service extraction.

| Track | Estimate |
|-------|----------|

The estimates assume current ECS accessors stay stable and no new major gameplay regression appears. Combat and item lifecycle phases dominate risk.

## 7. Parallel Work Opportunities

These can be parallelized after interfaces are agreed:

- NetworkSync snapshot extraction and Activity/Skill tail cleanup.
- Inventory/CItem service extraction and Quest Lua compatibility routing.
- Movement/AI callback extraction and Runtime header pruning.
- Documentation/test-plan work for packet, DB and Lua compatibility.

Do not parallelize Combat extraction with PointSystem/stat changes unless one owner controls both. That path has already produced high-risk regressions in earlier phases.

## 8. Risk Assessment

| Area | Risk | Reason |
|------|------|--------|
| Combat | High | Damage, drops, death, PvP, alignment and metin behavior all depend on it. |
| Item lifecycle | High | Persistence, ownership, trade, refine, sockets and inventory windows depend on exact state sync. |
| NetworkSync | High | Packet/client compatibility and visible state refresh depend on it. |
| Movement/AI | Medium | Sectree and position drift regressions are possible. |
| Quest Lua | Medium | Script compatibility must remain unchanged. |
| Activity/Skill/Mount tails | Medium | Feature-specific but narrower blast radius. |
| Runtime cleanup | Low | Mostly compile-time cleanup after blockers are removed. |

## 9. Feasibility Conclusion

Full deletion is feasible, but not as a single mechanical pass.

Minimum required before `CHARACTER` deletion:

- NetworkSync extraction.
- Combat extraction.
- Movement/AI callback extraction.
- Quest Lua compatibility routing.
- Runtime/header prune.

Minimum required before `CItem` deletion:

- Inventory/CItem mutation extraction.
- ItemSystem_LegacyBridge split/removal.
- Item lifecycle and event-state components.
- Item manager/DB service boundary isolation.

Can the project ship without full deletion? Yes.

Current state is shippable from an ECS migration perspective because read APIs are pure ECS and the remaining debt is isolated service/behavior debt. Full class deletion is architectural cleanup and risk reduction, not a prerequisite for the current migrated gameplay behavior to function.
