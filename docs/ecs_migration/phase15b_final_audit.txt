Step 4 - CHARACTER Member Coverage Gap (15C Readiness)

Rough structural counts:
- Total CHARACTER members in char.h: 237
- Total ECS component structs in ecs/components/*.hpp: 91

Coverage direction estimate:
- ECS component count is now large enough that the project has meaningful structural coverage for identity, vitals, transform/spatial, level/exp/gold, AI, combat-adjacent runtime, and several feature-specific domains.
- However, 91 component structs is not close to a one-to-one replacement for 237 CHARACTER members.
- Many CHARACTER members still represent large uncovered or only partially covered clusters, especially:
  - inventory/equipment authoritative storage
  - session/view/runtime wrapper state
  - event handles/timers
  - social links and classic runtime bookkeeping
  - remaining combat wrapper state

Interpretation:
- Phase 15C is viable, but it is not a near-finished cleanup. It would be real component expansion work, not just light follow-through.
- There is still a substantial CHARACTER-member coverage gap.

Step 5 - Recommendation

Decision:
- Favor Phase 15D first, with a small parallel 15C trickle only where it directly unblocks a concrete runtime pain point.

Why:
- A) Large remaining LPCHARACTER pool in non-ECS files: YES.
  - 880 of 940 remaining local declarations are outside ECS.
  - 1220 of 1327 remaining LPCHARACTER parameters are outside ECS.
  - 5857 of 6948 remaining direct ch->Method() calls are outside ECS.
  - This is the dominant remaining mass, and it is where the biggest mechanical reduction is available.
- B) Bridge-via-legacy-pointer pattern showing stress: SOMEWHAT, but not enough to override A.
  - The bridge pattern is now proven across 6 systems and has held up in runtime validation.
  - The remaining ECS surface is mostly intentional wrapper/runtime legacy, not accidental helper clutter.
  - There are still per-frame bridge calls, but the bigger blocker to project-wide LPCHARACTER elimination is simply that the non-ECS codebase still owns most of the usage.
- C) Split roughly even: NO.
  - The remaining surface is not evenly split. It is strongly skewed toward non-ECS code.

Recommended next direction:
1. Primary track: Phase 15D
   - Continue file-by-file LPCHARACTER reduction in non-ECS hotspots.
   - Best next targets by impact:
     - input_main.cpp
     - cmd_general.cpp
     - cmd_gm.cpp
     - questlua_pc.cpp
     - battle.cpp
     - char_manager.cpp
     - party.cpp
     - guild.cpp
     - questlua_dungeon.cpp
2. Secondary track: selective 15C only when needed
   - Expand components only where the lack of authority clearly blocks safe LPCHARACTER removal.
   - Most likely component-expansion triggers:
     - inventory/equipment authority
     - session/view/runtime wrapper state
     - remaining combat wrapper-owned runtime state
3. Practical strategy
   - Run 15D mechanically and aggressively on non-ECS hotspots.
   - Use 15C surgically, not as the main phase driver yet.

Bottom line:
- Phase 15B succeeded in cleaning the ECS runtime layer.
- The current numbers say the next major payoff is not another ECS-system cleanup pass.
- The next major payoff is non-ECS LPCHARACTER reduction, so the project should favor Phase 15D first.
- Phase 15C should follow as a targeted enabler, not as the primary next wave.
