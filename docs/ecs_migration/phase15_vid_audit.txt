Actual VID type definition
- File:
  - `SRC/Server/GameServer/vid.h`
- Definition kind:
  - `class VID`
- Shape:
  - private `uint32_t m_id`
  - private `uint32_t m_crc`
  - default ctor sets both to 0
  - ctor `(uint32_t id, uint32_t crc)`
  - copy ctor / assignment
  - `operator uint32_t() const` returns `m_id`
  - `Reset()` zeros both members
- Effective size:
  - logically 8 bytes (`2 x uint32_t`)
- Semantics:
  - not a typedef / alias
  - not a plain `uint32_t`
  - carries both numeric id and crc

CHARACTER-side VID storage
- `SRC/Server/GameServer/char.h:1067`
  - `VID m_vid;`
- `SRC/Server/GameServer/char.h:850`
  - `const VID& GetVID() const { return m_vid; }`

Other CHARACTER-side VID storage
- `SRC/Server/GameServer/char.h:2091`
  - `VID m_kVIDVictim;`
- `SRC/Server/GameServer/char.h:1704`
  - `typedef std::map<VID, TBattleInfo> TDamageMap;`

Immediate conclusion
- The legacy runtime does not use a trivial integer alias.
- Full elimination is not just “replace `uint32_t`”:
  - `m_crc`
  - victim tracking
  - damage maps
  must be accounted for.

Important implementation observations
- `CreateCharacter(...)` allocates a fresh legacy VID via `AllocVID()`
- `CreateCharacter(...)` inserts into `m_map_pkChrByVID` before ECS registration
  - `char_manager.cpp:371` `m_map_pkChrByVID.insert(std::make_pair(dwVID, ch));`

- CRC is therefore ignored by lookup authority today

Meaning
- Although `VID` carries `(id, crc)`, the authoritative map key is only `uint32_t`

  - unregisters from `CVIDRegistry`

Current `Find(...)` consumption
- `CVIDRegistry::Instance().Find(...)` lines in tree:
  - `50`
- Used broadly by:
  - AI helpers
  - combat
  - movement
  - session
  - quest
  - mount/horse
  - GM/admin utilities

Is every CHARACTER_MANAGER character also in CVIDRegistry?
- Answer:
  - not strictly guaranteed at every moment
- Why:
  - `CHARACTER_MANAGER::CreateCharacter(...)` inserts into `m_map_pkChrByVID` first
  - ECS registration happens later:
    - PC path in `input_db.cpp`
    - spawn path in `char_manager.cpp`
- Therefore there is a drift window:
  - legacy character exists in `m_map_pkChrByVID`
  - but corresponding `entt::entity` may not yet be registered in `CVIDRegistry`
- For fully initialized PCs / monsters / NPCs / stones:
  - the intended steady state is synchronized
- For transitional / failed / partially initialized lifetimes:
  - drift is possible

Migration implication
- `CVIDRegistry` is already the ECS-side bridge, but not yet safe as sole authority until creation-order drift is removed.

7. Migration strategy proposal
======================================================================

Phase A - single VID lookup authority
- Target:
  - `CHARACTER_MANAGER::Find(uint32_t)` and `Find(const VID&)` delegate to ECS-side registry resolution
  - legacy `m_map_pkChrByVID` becomes mirror-only, then removable
- Audit-driven workload:
  - `98` `CHARACTER_MANAGER::Find(...)` lines
  - `50` `CVIDRegistry::Find(...)` lines already exist
  - `16` references to `m_map_pkChrByVID`
- Difficulty:
  - medium/high
- Main blocker:
  - eliminate creation-order drift between legacy character creation and ECS registration

Phase B - collapse CHARACTER-side VID storage
- Target:
  - remove `CHARACTER::m_vid`
  - make `CHARACTER::GetVID()` read from ECS `VIDComponent`
  - then remove `GetVID()` from most gameplay paths
- Audit-driven workload:
  - `m_vid` storage
  - `m_kVIDVictim`
  - `TDamageMap = std::map<VID, ...>`
  - `7` raw `VID` declaration/signature lines from grep
  - true code sites are few, but high-risk because they are structural
- Difficulty:
  - high
- Main blocker:
  - victim / damage-map paths still use VID as internal runtime state

Phase C - replace `GetVID()` callers with entity-first flow
- Target:
  - callers stop fetching legacy VID and passing it around
  - they pass/store `entt::entity` directly
  - packet boundary converts entity -> `uint32_t` only on encode
- Audit-driven workload:
  - `50` files contain `->GetVID()`
  - many hot spots are combat/session/dungeon code
- Difficulty:
  - high but mechanical in many files
- Likely order:
  - quest / utility / admin files first
  - gameplay runtime later

Phase D - remove legacy VID class
- Target:
  - delete `class VID`
  - replace surviving packet-boundary needs with plain `uint32_t`
  - decide fate of `m_crc`
- Audit-driven workload:
  - class definition itself
  - any remaining `VID` parameters / locals / typedefs
  - packet and PvP helper structs already use `uint32_t`
- Difficulty:
  - medium if `m_crc` is truly dead
  - high if any runtime logic still relies on the CRC distinction

Most likely safest execution order
1. Phase A first:
   - make lookup authority singular
   - remove drift
2. Phase C second:
   - cut high-volume `GetVID()` traffic
3. Phase B third:
   - collapse `CHARACTER` storage after callers stop depending on it
4. Phase D last:
   - remove `VID` class only when internal runtime users are gone

======================================================================
8. Key risks / conclusions
======================================================================

Key risks
- `VID` is not a dumb alias:
  - it still carries `m_crc`
- `CHARACTER_MANAGER::Find(const VID&)` currently discards CRC:
  - this suggests semantic rot and makes the type removal easier conceptually
  - but also means hidden assumptions may already be broken
- `CVIDRegistry` is not yet guaranteed in sync at all times:
  - creation-order drift exists today
- `m_kVIDVictim` and `TDamageMap<VID,...>` are internal blockers:
  - these are not packet-boundary uses
  - they must be redesigned, not just search-replaced

Bottom line
- VID unification is feasible.
- The highest-value first cut is not deleting `VID` itself.
- The highest-value first cut is:
  - make `CVIDRegistry` / ECS lookup authoritative
  - remove the `m_map_pkChrByVID` authority role
  - then progressively eliminate `GetVID()` and internal `VID` state.
