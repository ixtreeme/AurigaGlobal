Phase 15B-1 — GayaSystem entity-first pilot

Date: 2026-04-19
Build gate: PASS

Scope
- File: SRC/Server/GameServer/ecs/systems/GayaSystem.cpp
- Helper: SRC/Server/GameServer/ecs/AIHelpers.hpp

Step 1 audit summary
- GayaSystem public API was already entity-based in GayaSystem.hpp.
- Internal implementation still used a local helper that resolved entity -> VIDComponent -> CHARACTER_MANAGER::Find(...).
- Internal state authority is still legacy CHARACTER-owned:
  - load_gaya_items
  - load_gaya_values
  - info_items
  - info_slots
  - GayaUpdateTime
  - GetGaya / PointChange(POINT_GAYA)
- No direct external callers to GayaSystem::* were found outside the file-local CHARACTER wrappers.
- External gameplay callers still use CHARACTER wrappers such as:
  - CraftGayaItems
  - MarketGayaItems
  - RefreshGayaItems
  - UpdateItemsGayaMarker
  - InfoGayaMarker

Step 2 caller audit
- Direct external GayaSystem::* callers: 0
- Caller cascade risk: low
- Existing wrapper model:
  - CHARACTER::* methods bridge to GayaSystem::* via AIHelpers::EcsOf(this)

Step 3 signature decisions
- Load: OPTION_ENTITY (already entity)
- CheckItemsFull: OPTION_ENTITY
- ClearMarket: OPTION_ENTITY
- InfoMarket: OPTION_ENTITY
- CheckSlot: OPTION_ENTITY
- BuyItems: OPTION_ENTITY
- RefreshItemsMarket: OPTION_ENTITY
- UpdateSlot: OPTION_ENTITY
- UpdateItems0: OPTION_ENTITY
- UpdateItems: OPTION_ENTITY
- CraftItems: OPTION_ENTITY
- MarketItems: OPTION_ENTITY
- RefreshItems: OPTION_ENTITY
- GetState: OPTION_ENTITY
- SetState: OPTION_ENTITY
- StartCheckTimeMarket: OPTION_ENTITY

No KEEP_LEGACY_OVERLOAD was needed because the wrapper layer already existed on CHARACTER.

Implementation pattern summary
- Pattern A (read from ECS component instead of CHARACTER): 0
  - Reason: no dedicated ECS Gaya component / market-state component exists yet.
  - Gaya data coverage remains a Phase 15D component-expansion concern.

- Pattern B (legacy mutating authority through one resolved CHARACTER bridge): 8
  - ClearMarket
  - BuyItems
  - UpdateSlot
  - UpdateItems0
  - UpdateItems
  - CraftItems
  - RefreshItems
  - SetState

- Pattern C (legacy packet/chat/event interaction through one resolved CHARACTER bridge): 6
  - check_time_market_event
  - InfoMarket
  - BuyItems
  - CraftItems
  - MarketItems
  - RefreshItems

- Pattern D (resolve legacy pointer once at top of entity-entry function): 16
  - Every GayaSystem entity-entry function now begins with a single:
    auto* ch = LegacyCharOf(entity);
  - The old repeated entity -> VIDComponent -> Find(...) pattern is gone.

Concrete changes
- Replaced local entity -> CHARACTER resolution from:
  - VIDComponent + CHARACTER_MANAGER::Find(...)
  to:
  - LegacyCharPtr component lookup
- Removed dependency on char_manager.cpp lookup from GayaSystem internals.
- Added AIHelpers::EcsOf(const CHARACTER*) overload to remove const_cast noise from the const wrapper path.

Counts
- Baseline LPCHARACTER count from migration audit: 17
- Post-migration raw LPCHARACTER / CHARACTER* token count in GayaSystem.cpp/.hpp: 0
- LegacyCharOf bridge points in GayaSystem entity-entry functions: 16

What went smoothly
- Public GayaSystem surface was already entity-first, so no caller cascade was needed.
- Existing CHARACTER wrappers made the migration low-risk.
- LegacyCharPtr component was already available and stable after VID-A.

Unexpected friction
- char_event_info::ch is DynamicCharacterPtr, not a raw CHARACTER pointer.
  - Correct access is info->ch.Get().
- MSVC rejected mixed auto return deduction for pointer + nullptr in the local helper.
  - Fixed by using an explicit LegacyCharHandle alias.

Recommendation for next targets
- AffectSystem
  - Good next candidate if handled as targeted helper cleanup first.
  - It already mixes ECS events with legacy pointers and has similar bridge opportunities.
- SkillSystem
  - Higher risk than GayaSystem.
  - Better after one or two more small/medium pilots, because it has deeper combat/runtime coupling.

Recommendation for Phase 15B reuse
- Prefer entity-first public signatures.
- Keep legacy authority behind exactly one local bridge per function.
- Replace entity -> Find(...) with entity -> LegacyCharPtr wherever state authority still lives on CHARACTER.
- Do not attempt ECS component expansion in the same pass as bridge cleanup.

Implementation pattern summary

  - load_affect_login_event
  - test_server info-chat branches in poison/bleed/fire application

- Pattern D (resolve legacy pointer once at top of entity-entry function): 13
  - All AffectSystem namespace entity-entry functions now use a single:
    auto* ch = LegacyCharOf(entity);

Concrete changes
- Replaced local entity -> CHARACTER resolution from:
  - VIDComponent + CHARACTER_MANAGER::Find(...)
  to:
  - LegacyCharPtr component lookup
- Converted raw LPCHARACTER locals to `auto*` bridge locals.
- Converted DynamicCharacterPtr event access from:
  - info->ch
  to:
  - info->ch.Get()
- Converted registry iteration from:
  - view<AffectList, VIDComponent> + Find(vid.value)
  to:
  - view<AffectList, LegacyCharPtr> + legacy.ptr

Lifecycle safety findings
- Affect event callbacks already had the correct null-safe shape:
  - if event info is null -> return 0
  - if resolved character is null -> return 0
- The critical teardown-safe pattern here is:
  - resolve from DynamicCharacterPtr or LegacyCharPtr
  - null-check before dereference
  - avoid re-looking up through CHARACTER_MANAGER when the entity already carries LegacyCharPtr
- No extra ECS-side cleanup path was introduced because AffectList still mirrors legacy affect ownership.

Counts
- Baseline LPCHARACTER count from audit: 32
- Post-migration raw LPCHARACTER / CHARACTER* token count in AffectSystem.cpp/.hpp: 3
- Intentional survivors: 3
  - all three are CHARACTER wrapper signatures for attacker input
- Accidental survivors: 0

What went smoothly
- AffectSystem namespace API was already entity-first, so there was no caller cascade.
- LegacyCharPtr again proved to be the correct bridge after VID-A.
- The event/lifecycle code already had most of the required null checks; the main cleanup was the lookup path, not the control flow.

Unexpected friction
- The baseline count was higher than the old audit estimate because this file still contains large legacy CHARACTER-affect implementations below the AffectSystem namespace.
- The important distinction was:
  - AffectSystem namespace internals
  versus
  - legacy CHARACTER wrapper / implementation code living in the same compilation unit

  - next logical step, but higher risk than AffectSystem
  - should reuse the same LegacyCharPtr bridge cleanup first

  - defer until after one more medium-risk successful system pass


Phase 15B-3 - SkillSystem entity-first cleanup

Scope
- File: SRC/Server/GameServer/ecs/systems/SkillSystem.cpp
- SkillSystem.hpp needed no signature expansion in this pass.
- Existing VID-A6 groundwork remained in place:
  - CheckSkillHit(attacker, skillId, target) already entity-based
  - CheckSkillHitCount already entity-based
  - TSkillUseInfo::dwVID is entt::entity
  - TSkillUseInfo::target_map is std::map<entt::entity, size_t>

Audit summary
- Baseline raw LPCHARACTER / CHARACTER* token count in SkillSystem.cpp/.hpp: 42
- External direct SkillSystem::* callers outside the file were effectively negligible.
- The practical entry chain still comes through CHARACTER wrapper methods such as:
  - UseSkill
  - ComputeSkill
  - ComputeSkillParty
  - ComputeGyeongGongSkill
- High-risk internal hotspots before cleanup were:
  - LegacyCharacter(entity) using VIDComponent + CHARACTER_MANAGER::Find(...)
  - chain_lightning_event payload using runtime ids resolved later
  - splash functors carrying LPCHARACTER state
  - event callbacks reading DynamicCharacterPtr as raw pointer

Signature decisions
- Namespace-level entity-entry helpers stayed OPTION_ENTITY.
- No wide external caller cascade was needed.
- Large CHARACTER runtime wrappers stayed intentionally legacy for now:
  - int CHARACTER::ComputeSkillParty(uint32_t, LPCHARACTER, uint8_t)
  - int CHARACTER::ComputeGyeongGongSkill(uint32_t, LPCHARACTER, uint8_t)
  - int CHARACTER::ComputeSkill(uint32_t, LPCHARACTER, uint8_t)
  - bool CHARACTER::UseSkill(uint32_t, LPCHARACTER, bool)
- These 4 wrappers are the only raw LPCHARACTER survivors after the pass.

Implementation pattern summary
- Pattern A (pure ECS reads replacing CHARACTER reads): 0
  - Skill authority still ultimately flows through legacy CHARACTER runtime logic.
  - This pass only removed the old VID-based bounce-back lookup path.

- Pattern B (legacy mutating authority through one resolved CHARACTER bridge): 9
  - IsLearnableSkill
  - LearnGrandMasterSkill
  - LearnSkillByBook
  - CanUseMobSkill
  - CanUseSkill
  - CheckSkillHit
  - ComputeCooltime
  - ResetSkill
  - chain_lightning_event victim/caster resolution

- Pattern C (legacy packet/event/combat interaction through one resolved CHARACTER bridge): 6
  - skill_muyoung_event
  - skill_gyeongGong_event
  - mob_skill_hit_event
  - chain_lightning_event
  - FuncSplashDamage
  - FuncSplashAffect

- Pattern D (resolve legacy pointer once at top of entity-entry function): 11
  - All cleaned entity-entry helpers now use a single LegacyCharOf(entity) lookup.

Concrete changes
- Replaced local entity -> CHARACTER resolution from:
  - VIDComponent + CHARACTER_MANAGER::Find(...)
  to:
  - LegacyCharPtr component lookup
- Added a local bridge alias:
  - using LegacyCharHandle = decltype(std::declval<ecs::LegacyCharPtr>().ptr);
- Updated helper/functor members and parameters from LPCHARACTER to LegacyCharHandle:
  - FFindNearVictim
  - FuncSplashDamage
  - FuncSplashAffect
  - FComputeSkillParty
  - FHealerParty
- Converted chain_lightning_event payload from runtime uint32 ids to entt::entity:
  - dwVictim: entt::entity
  - dwChr: entt::entity
- Converted event callback access from:
  - info->ch
  to:
  - info->ch.Get()
- Removed unnecessary const_cast in CHARACTER const wrappers by using:
  - AIHelpers::EcsOf(this)

Lifecycle / null-safety findings
- Skill teardown edges are more dangerous than Gaya or Affect because both attacker and victim may disappear mid-chain.
- The safe pattern for this pass is:
  - resolve attacker once
  - resolve target once
  - abort or skip when either side is missing
- chain_lightning_event is now safer because it no longer stores packet ids that must be re-routed through a later Find(...).
- DynamicCharacterPtr event payloads must always be read with .Get() before dereference.

Counts
- Baseline LPCHARACTER count from audit: 42
- Post-migration raw LPCHARACTER / CHARACTER* token count in SkillSystem.cpp/.hpp: 4
- Intentional survivors: 4
  - all four are large CHARACTER wrapper signatures listed above
- Accidental survivors: 0
- LegacyCharOf bridge points in SkillSystem.cpp/.hpp: 11

What went smoothly
- VID-A6 groundwork had already converted target tracking and hit-count bookkeeping to entt::entity.
- LegacyCharPtr again proved to be the right bridge after VID elimination.
- Helper/functor cleanup was straightforward once the old Find(...) bounce was removed.

Unexpected friction
- The baseline token count was materially higher than the original phase estimate because SkillSystem.cpp still hosts a very large amount of legacy CHARACTER runtime code.
- The file mixes three layers in one compilation unit:
  - entity-entry helpers
  - event/functor glue
  - legacy CHARACTER skill runtime
- That means token-count reduction is useful, but must be interpreted carefully.

- Boot/log smoke: PASS
- No fresh skill-specific null-deref, VID_DRIFT, DestroyCharacter, or SpawnMob regression was observed in the fresh boot window.
- Full in-client skill gameplay still requires manual smoke for:
  - single-target skill damage
  - AoE skill damage
  - buff/debuff application
  - death/logout/channel edge cases
