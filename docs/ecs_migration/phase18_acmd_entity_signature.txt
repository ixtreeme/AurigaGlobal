Phase 18 - ACMD command handler entity signature flip
Date: 2026-09-01

Scope
-----
Continuation of the "OOP - ECS konverzio eltuntetes" batches (d8ec8cb, 6cc076f).
Those commits inlined AIHelpers::EcsOf(x) into the explicit form
((x) ? (x)->GetEntityHandle() : entt::null) so every remaining OOP->ECS
conversion point became greppable. This phase removes that conversion from the
whole chat-command surface by pushing the entity up into the handler signature.

Signature change
----------------
cmd.h:
  #define ACMD(name)  void (name)(LPCHARACTER ch, ...)
    ->
  #define ACMD(name)  void (name)(entt::entity character, ...)

  struct command_info::command_pointer follows the same flip.

cmd.cpp:
  interpret_command(entt::entity, ...) is now the primary implementation; it
  resolves the legacy pointer once (ecs::LegacyCharOf) for the anti-flood /
  position gates and dispatches the entity to the handler.
  interpret_command(LPCHARACTER, ...) is now a one-line wrapper kept for the
  remaining legacy call sites.

Handler body rule
-----------------
Inside each ACMD body:
  - ((ch) ? (ch)->GetEntityHandle() : entt::null)  ->  character
  - handlers that still call legacy CHARACTER methods get exactly one alias at
    the top of the body:
        LPCHARACTER ch = ecs::LegacyCharOf(character);
    so every remaining ch-> call site is textually unchanged and the legacy
    surface stays trivially greppable for the next phase.

Phase 18c - CHARACTER_MANAGER consumer API entity flip
-------------------------------------------------------
char_manager.cpp had 219 conversion sites (the where.py breakdown counts both
the ((p) ? ...) and the (p ? ...) spellings). They split into two kinds, and
each kind got the treatment it deserves.

A. Signature flip - methods that only *consume* a character
   14 declarations in char_manager.h moved to entt::entity:

     CheckEventForDrop(pkChr, pkKiller, ...)  -> (character, killer, ...)   96
     LoadItemShopBuyReal                                                     8
     LoadItemShopBuy                                                         6
     LoadItemShopLog                                                         3
     LoadItemShopLogReal                                                     2
     LoadItemShopData(ch, isAll)                                             2
     PacketMonsterLog                                                        3
     SendDataPlayer                                                          2
     CheckBonusEvent                                                         2
     GetMobDamageRate / GetMobGoldAmountRate / GetMobGoldDropRate /
     GetMobExpRate / GetUserDamageRate                                       6

   CheckEventForDrop alone was 96 of them - 93 repetitions of the same
   ((pkChr) ? ...) inside one 380-line boss/metin drop-event chain.

   The four premium-gated rate getters were rewritten rather than aliased:
   `ch->GetPremiumRemainSeconds(X)` is already a pure forward to
   ecs::PlayerRuntime::GetPremiumRemainSeconds, which returns 0 for a null or
   invalid entity - so the `if (!ch) return <base rate>;` guard was exactly
   redundant with the premium check and could go.

   GetMobItemRate(LPCHARACTER) was a dead forwarder to the entity overload that
   already existed; its only caller already passed an entity. Deleted.

   62 external call sites were checked; only 14 actually needed touching
   (battle.cpp, cmd_general.cpp, CombatSystem.cpp x9, PlayerRuntimeSystem.cpp,
   StatSystem.cpp, input_db.cpp x2, input_login.cpp, item_manager.cpp). Where
   the caller still holds a real pointer the conversion moved outward to it -
   that is the point: it now sits at the one place a pointer still lives.

B. Hoist - functions that own a local pointer and re-converted it N times
   No signature change; the repeated conversion collapses onto one local:

     SpawnMob 12, SpawnMobRandomPosition 11, DestroyCharacter 8, Update 6,
     SpawnMoveGroup 5, SpawnGroup 4, SpawnMobRange 3, FindSpecifyPC 3,
     the anonymous-namespace alive-VID sweep 3, FindByPID 2, FindPC 2,
     SetEventStatus 2, RegisterRaceNumMap 2, UnregisterRaceNumMap 2,
     RefreshItemShop 1

   These are factory / lookup / lifetime functions. Their LPCHARACTER is the
   legacy identity boundary itself, so flipping their signature belongs to a
   later identity phase, not to this one.

Left in place (25 sites)
------------------------
  - 18 are LPITEM subjects (rewardItem, extraDrop, item) - a different axis.
  - 3 are the `c` loop variable over m_set_pkChrMonsterLog, a pointer set.
  - 4 are lone conversions inside ENABLE_INGAME_DEBUG_RAZOR93 blocks in
    AddToStateList / RemoveFromStateList / RegisterForMonsterLog /
    UnregisterForMonsterLog. Those methods genuinely operate on CHARACTER_SET
    pointer containers; flipping them would only add a LegacyCharOf round-trip.

Phase 18d - battle.h / battle.cpp full entity flip
---------------------------------------------------
The whole battle API is now entity-native. This is the first file in the
migration that ends at *zero* inlined conversions, header included.

battle.h - 14 declarations + 2 inline definitions flipped:

  CalcAttackRating, battle_is_attackable, battle_melee_attack, battle_end,
  battle_distance_valid, NormalAttackAffect, and the ENABLE_ANTICHEAT quartet
  GET_ATTACK_SPEED / SET_ATTACK_TIME / SET_ATTACKED_TIME / IS_SPEED_HACK.

  The two inline helpers AttackAffect (11 conversions) and SkillAttackAffect
  (5) had *zero* legacy pointer uses in their bodies - pure flips, no alias
  needed. They are now entity-only from signature to last statement.

battle.cpp - 19 definitions, 195 conversion sites removed:
  CalcAttBonus 56, battle_hit 36, battle_melee_attack 24, CalcMeleeDamage 23,
  CalcArrowDamage 18, battle_is_attackable 17, IS_SPEED_HACK 10,
  NormalAttackAffect 8, battle_distance_valid 4, plus 9 smaller ones.

Naming convention settled here
------------------------------
After this pass, inside the battle code:
  attacker / victim / character  always mean entt::entity
  pkAttacker / pkVictim / ch     always mean LPCHARACTER
Functions whose parameter was already named `victim` as a pointer had their
remaining pointer uses renamed to pkVictim, so the entity could take the good
name. That rename is compiler-checked in both directions: entt::entity is an
enum class, so it has no operator-> and no implicit conversion to a pointer -
any mix-up is a hard error, never a silent behaviour change.

Call sites
----------
41 external call sites in 5 files were adapted (cmd_gm.cpp, AffectSystem.cpp,
CombatSystem.cpp, NetworkSyncSystem.cpp, SkillSystem.cpp) plus 24 intra-file
calls. Each file kept its own local spelling of the conversion.
NetworkSyncSystem.cpp carried a private `extern bool battle_is_attackable(
LPCHARACTER, LPCHARACTER);` redeclaration that had to move with the header.

Tooling note
------------
The parameter-flip helper had a placeholder collision: it substituted each
conversion with "\0<entityName>\0", so when a parameter was being renamed to
its own name (victim -> victim) the later bare-use scan matched the
placeholders themselves and rewrote entity slots back into pointer uses. The
first battle.cpp run was reverted and the helper switched to opaque, indexed
placeholders. Earlier phases were unaffected: their entity names (character,
killer, attacker) never matched their parameter names (ch, pkChr, pkKiller,
pkAttacker) as whole words.

Left in place
-------------
  - battle.h still declares `extern int battle_count_attackers(LPCHARACTER ch);`
    That function has no definition and no caller anywhere in the tree; it is a
    dead declaration, not a migration target.
  - one conversion inside a commented-out line in CalcArrowDamage, on an LPITEM
    subject (pkBow).

battle.cpp: 195 -> 0 (1 in a comment)   battle.h: 16 -> 0
Project-wide conversion count: 4743 -> 4568

std::bind caught what the eye missed
------------------------------------
Seven for_each/std::bind sites in guild.cpp bound a now-entity member function
over m_memberOnline, which is a CHARACTER_SET:

  for_each(m_memberOnline.begin(), m_memberOnline.end(),
           std::bind(&CGuild::SendSkillInfoPacket, this, _1));

std::bind defers the type check into the binder's operator(), so this reports
as "attempting to reference a deleted function" deep inside <algorithm> with
no line number in our own code. Each one was rewritten as an explicit loop
that converts at the point of call. Worth remembering for the remaining files:
grep for std::bind over any method being flipped, the compiler will not point
at the call site.

Phase 18f - dungeon group hook API entity flip
-----------------------------------------------
Ten C++ dungeon classes share one hook API. They were migrated as a group.

  CEasterDungeon, CHalloween2022Dungeon, CLostCastleDungeon,
  CNightmareDungeonRazor93, COrcsDungeon, CPyramidDungeonRazor93,
  CRuneDungeon, CTritonTempleDungeon, CValentineDungeon, CVikingDungeon

Common shape:
  OnPlayerLogin(ch) / OnPlayerDisconnect(ch) / OnMobKilled(killer, victim)
  OnClickNpc(ch[, npc]) / OnNpcTakeItem(from, npc, item) / OnUseItem*(ch)
plus LostCastle's CheckCloneDamage(attacker, victim) and
SpawnTestClones(source, target, count).

51 method definitions flipped, 48 declarations across the 10 headers,
49 hook call sites adapted in 6 files:
  trigger.cpp (OnClickNpc x10), input_login.cpp (OnPlayerLogin x10),
  SessionSystem.cpp (OnPlayerDisconnect x9), CombatSystem.cpp (OnMobKilled x11),
  ItemSystem_LegacyBridge.cpp (OnNpcTakeItem / OnUseItem x8), ItemUse.cpp (x1).

Naming rule for this group
--------------------------
These files spell the pointer as `CHARACTER*`, not LPCHARACTER, so the tooling
had to learn both spellings. The entity keeps the semantic name and the legacy
alias takes the codebase's pk prefix:

  ch      -> entity `character`, alias stays `ch` (as in every earlier phase)
  killer  -> entity `killer`,  alias `pkKiller`
  victim  -> entity `victim`,  alias `pkVictim`
  npc / from / attacker / source / target likewise.

Every dungeon .cpp gained #include "ecs/CharacterAccessors.hpp", and every
dungeon .h gained #include <entt/entt.hpp>.

Note on LostCastle
------------------
Every CLostCastleDungeon hook call site in the tree is currently commented out
(trigger.cpp, CombatSystem.cpp, ItemSystem_LegacyBridge.cpp, cmd_gm.cpp). The
class was migrated anyway so the group stays uniform, and the commented call
sites were rewritten with it so they still match if re-enabled.

Dungeon group: 819 -> 351 conversion sites
Project-wide conversion count: 4350 -> 3909

Still open in this group (351 sites), one shape
-----------------------------------------------
Each dungeon file carries its own copy of

  inline void ForEachPcOnMap(int32_t mapIndex,
                             const std::function<void(LPCHARACTER)>& fn)

and the lambdas passed to it re-convert their LPCHARACTER parameter on every
line. Flipping that std::function to void(entt::entity) would push the entity
into every lambda in all ten files at once - that is the natural next step for
this group, and it is a different shape from the hook flip, so it gets its own
pass.


Phase 18g - dungeon group, pass 2: ForEachPcOnMap
--------------------------------------------------
The shape phase 18f left open. Every dungeon file carries its own copy of a
per-map PC iterator, in two spellings:

  A) inline void ForEachPcOnMap(int32_t, const std::function<void(LPCHARACTER)>&)
     (7 files, plus PyramidDungeonRazor93's hand-rolled collector variant)
  B) template <typename F> void ForEachPcOnMap(int32_t, F&&)
     (Halloween2022, RuneDungeon, VikingDungeon)

Both now hand over an entt::entity, converting exactly once at the iterator's
own PC check. 65 lambdas flipped across the ten files, 178 conversion sites
removed inside them; 62 kept a pk-prefixed alias for their remaining pointer
use.

Two follow-on shapes had to be handled
--------------------------------------
1. Named lambdas (applyMember, checkMember, setupMember, prepareMember, fn,
   check, removeEntranceItems) are both passed to ForEachPcOnMap *and* invoked
   directly on the single-player path: `if (!party) applyMember(ch);`. Those
   invocations now pass the entity already in scope.

2. CParty::ForEach*Member still calls back with an LPCHARACTER, and it takes
   Func& - an lvalue. Nine sites in four files handed a now-entity lambda to
   it. Each got a named pointer->entity adapter:

     auto checkMemberPtr = [&](LPCHARACTER pkMember) {
         checkMember(pkMember ? pkMember->GetEntityHandle() : entt::null); };

   Flipping CParty's iterators themselves would reach dungeon.cpp,
   CombatSystem, ItemSystem_LegacyBridge, SocialSystem, questlua_* and
   input_main - a separate phase.

Two tooling bugs, caught and reverted
-------------------------------------
The first attempt at this pass was reverted whole rather than patched:

- The lambda-invocation fixer rewrote the string in place while iterating a
  match list computed on the *old* string, so every match after the first used
  a stale offset. It produced `applyMember(m)er(pkM);` - a syntax error, so the
  compiler caught it, but the same bug in a whole-word-safe rewrite could have
  landed silently. The fixer now builds the output in one pass.
- The CParty adapter was inserted at the call site, which is often a braceless
  `if (party) ...` branch, turning one statement into two and detaching the
  `else`. Adapters are now declared right after the lambda they wrap, which is
  always at statement scope.
