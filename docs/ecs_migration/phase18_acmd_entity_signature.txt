Phase 18 - ACMD command handler entity signature flip
Date: 2026-09-01

Scope
-----
Continuation of the "OOP - ECS konverzio eltuntetes" batches (d8ec8cb, 6cc076f).
Those commits inlined AIHelpers::EcsOf(x) into the explicit form
((x) ? (x)->GetEntityHandle() : entt::null) so every remaining OOP->ECS
conversion point became greppable. This phase removes that conversion from the
whole chat-command surface by pushing the entity up into the handler signature.

Signature change
----------------
cmd.h:
  #define ACMD(name)  void (name)(LPCHARACTER ch, ...)
    ->
  #define ACMD(name)  void (name)(entt::entity character, ...)

  struct command_info::command_pointer follows the same flip.

cmd.cpp:
  interpret_command(entt::entity, ...) is now the primary implementation; it
  resolves the legacy pointer once (ecs::LegacyCharOf) for the anti-flood /
  position gates and dispatches the entity to the handler.
  interpret_command(LPCHARACTER, ...) is now a one-line wrapper kept for the
  remaining legacy call sites.

Handler body rule
-----------------
Inside each ACMD body:
  - ((ch) ? (ch)->GetEntityHandle() : entt::null)  ->  character
  - handlers that still call legacy CHARACTER methods get exactly one alias at
    the top of the body:
        LPCHARACTER ch = ecs::LegacyCharOf(character);
    so every remaining ch-> call site is textually unchanged and the legacy
    surface stays trivially greppable for the next phase.

Naming convention settled here
------------------------------
After this pass, inside the battle code:
  attacker / victim / character  always mean entt::entity
  pkAttacker / pkVictim / ch     always mean LPCHARACTER
Functions whose parameter was already named `victim` as a pointer had their
remaining pointer uses renamed to pkVictim, so the entity could take the good
name. That rename is compiler-checked in both directions: entt::entity is an
enum class, so it has no operator-> and no implicit conversion to a pointer -
any mix-up is a hard error, never a silent behaviour change.

Call sites
----------
41 external call sites in 5 files were adapted (cmd_gm.cpp, AffectSystem.cpp,
CombatSystem.cpp, NetworkSyncSystem.cpp, SkillSystem.cpp) plus 24 intra-file
calls. Each file kept its own local spelling of the conversion.
NetworkSyncSystem.cpp carried a private `extern bool battle_is_attackable(
LPCHARACTER, LPCHARACTER);` redeclaration that had to move with the header.

Tooling note
------------
The parameter-flip helper had a placeholder collision: it substituted each
conversion with "\0<entityName>\0", so when a parameter was being renamed to
its own name (victim -> victim) the later bare-use scan matched the
placeholders themselves and rewrote entity slots back into pointer uses. The
first battle.cpp run was reverted and the helper switched to opaque, indexed
placeholders. Earlier phases were unaffected: their entity names (character,
killer, attacker) never matched their parameter names (ch, pkChr, pkKiller,
pkAttacker) as whole words.

    That function has no definition and no caller anywhere in the tree; it is a
    dead declaration, not a migration target.
  - one conversion inside a commented-out line in CalcArrowDamage, on an LPITEM
    subject (pkBow).

std::bind caught what the eye missed
------------------------------------
Seven for_each/std::bind sites in guild.cpp bound a now-entity member function

These files spell the pointer as `CHARACTER*`, not LPCHARACTER, so the tooling
had to learn both spellings. The entity keeps the semantic name and the legacy

  ch      -> entity `character`, alias stays `ch` (as in every earlier phase)
  killer  -> entity `killer`,  alias `pkKiller`
  victim  -> entity `victim`,  alias `pkVictim`
  npc / from / attacker / source / target likewise.

dungeon .h gained #include <entt/entt.hpp>.

Still open in this group (351 sites), one shape
-----------------------------------------------
Each dungeon file carries its own copy of

  inline void ForEachPcOnMap(int32_t mapIndex,
                             const std::function<void(LPCHARACTER)>& fn)

and the lambdas passed to it re-convert their LPCHARACTER parameter on every
line. Flipping that std::function to void(entt::entity) would push the entity
into every lambda in all ten files at once - that is the natural next step for
this group, and it is a different shape from the hook flip, so it gets its own
pass.


Phase 18g - dungeon group, pass 2: ForEachPcOnMap
--------------------------------------------------
The shape phase 18f left open. Every dungeon file carries its own copy of a
per-map PC iterator, in two spellings:

  A) inline void ForEachPcOnMap(int32_t, const std::function<void(LPCHARACTER)>&)
     (7 files, plus PyramidDungeonRazor93's hand-rolled collector variant)
  B) template <typename F> void ForEachPcOnMap(int32_t, F&&)
     (Halloween2022, RuneDungeon, VikingDungeon)

Both now hand over an entt::entity, converting exactly once at the iterator's
own PC check. 65 lambdas flipped across the ten files, 178 conversion sites
removed inside them; 62 kept a pk-prefixed alias for their remaining pointer
use.

Two follow-on shapes had to be handled
--------------------------------------
1. Named lambdas (applyMember, checkMember, setupMember, prepareMember, fn,
   check, removeEntranceItems) are both passed to ForEachPcOnMap *and* invoked
   directly on the single-player path: `if (!party) applyMember(ch);`. Those
   invocations now pass the entity already in scope.

2. CParty::ForEach*Member still calls back with an LPCHARACTER, and it takes
   Func& - an lvalue. Nine sites in four files handed a now-entity lambda to
   it. Each got a named pointer->entity adapter:

     auto checkMemberPtr = [&](LPCHARACTER pkMember) {
         checkMember(pkMember ? pkMember->GetEntityHandle() : entt::null); };

   Flipping CParty's iterators themselves would reach dungeon.cpp,
   CombatSystem, ItemSystem_LegacyBridge, SocialSystem, questlua_* and
   input_main - a separate phase.

Two tooling bugs, caught and reverted
-------------------------------------
The first attempt at this pass was reverted whole rather than patched:

- The lambda-invocation fixer rewrote the string in place while iterating a
  match list computed on the *old* string, so every match after the first used
  a stale offset. It produced `applyMember(m)er(pkM);` - a syntax error, so the
  compiler caught it, but the same bug in a whole-word-safe rewrite could have
  landed silently. The fixer now builds the output in one pass.
- The CParty adapter was inserted at the call site, which is often a braceless
  `if (party) ...` branch, turning one statement into two and detaching the
  `else`. Adapters are now declared right after the lambda they wrap, which is
  always at statement scope.

Phase 18h - identity boundary: entity-returning lookups
--------------------------------------------------------
AUDIT FIRST. Before touching anything, every site that assigns from a
CHARACTER_MANAGER lookup or factory was measured:

  api                     sites   conversions   remaining pointer uses
  FindByPID                  40           222                      495
  Find                       40           170                      237
  CreateCharacter             5            51                      135
  FindPC                     30            44                       68
  SpawnMob                   30            33                       73
  (+ SpawnMobRange, SpawnMobRandomPosition, FindSpecifyPC)
  TOTAL                     150           531                     1035

The conclusion matters more than the numbers: flipping the whole lookup API's
return type would remove 531 conversions but leave 1035 real legacy CHARACTER
method calls behind, each needing a LegacyCharOf alias. It would relocate work
rather than remove it, and it would make ~118 sites temporarily *worse*
(entity + immediate alias + split null handling).

So the identity boundary is being opened where it is genuinely free, not
big-bang. What actually blocks those 1035 uses is the legacy method surface,
not the lookup API.

What was added
--------------
char_manager.h/.cpp gained three entity-returning counterparts:

  entt::entity FindEntity(uint32_t dwVID);
  entt::entity FindPCEntity(const char* name);
  entt::entity FindEntityByPID(uint32_t dwPID);

FindEntity goes straight to CVIDRegistry - which is already the ECS-side
authority for VID -> entity, and which Find() already consults first, logging
VID_DRIFT when it has to fall back. The other two convert once inside the
manager. No new bookkeeping, no second source of truth, no drift risk.

What was migrated
-----------------
33 sites in 12 files where the looked-up local is *only* ever fed to
conversions and null tests. At those sites the pointer disappears completely:

  -  LPCHARACTER pkChr = CHARACTER_MANAGER::instance().FindByPID(info->dwPID);
  -  if (pkChr == nullptr) return 0;
  -  ... GetMapIndex(((pkChr) ? (pkChr)->GetEntityHandle() : entt::null)) ...
  +  const entt::entity pkChr = CHARACTER_MANAGER::instance().FindEntityByPID(info->dwPID);
  +  if (pkChr == entt::null) return 0;
  +  ... GetMapIndex(pkChr) ...

68 conversions removed, plus 20 boolean uses made explicit (entt::entity has
no conversion to bool, so `if (v)` had to become `if (v != entt::null)`).

Three tooling failures on the way, all reverted whole rather than patched
------------------------------------------------------------------------
This pass was rewritten from scratch three times. Worth recording, because the
first two mistakes are the kind that can land silently:

1. Multiple edits inside one function body: the driver spliced the file per
   edit while other recorded edits still pointed into the old text. Now one
   edit per body per pass, and the driver re-runs until a pass is empty.

2. The "is this local only used through conversions?" test accepted any use
   preceded by "(", so `if (pkVictim->GetArena())` and
   `make_pair(key, ch)` counted as null tests. It is now a strict whitelist of
   exact null/truth-test shapes; anything else disqualifies the site.

3. The conversion regex allowed the parentheses to be optional on both sides,
   so against the single-paren spelling it swallowed the *enclosing call's*
   parenthesis:
       GetPacketVID(v ? v->GetEntityHandle() : entt::null)  ->  GetPacketVIDv
   It now matches three explicit shapes and never consumes a paren that
   belongs to a caller. Earlier phases were checked and are unaffected - their
   helpers only ever matched the fully-parenthesised double form.

Build: RelWithDebInfo GameServer, 0 errors.

Next, in the order the audit suggests
-------------------------------------
Do NOT flip the lookup return types wholesale yet. The 1035 pointer uses are
legacy CHARACTER methods; migrate that surface first (new_offlineshop_manager
127, party 113, item_manager 80, ...). Every method that moves shrinks the
pointer count at the lookup sites, and the identity flip gets cheaper each
time. Re-run the audit to decide when it has tipped.

Phase 18m - UseItemEx: the one function the hoist had to refuse
----------------------------------------------------------------
After the tree-wide sweep, an audit of LPITEM-parameter functions showed 149
conversions across 36 functions - and 113 of them in a single one:

    bool CHARACTER::UseItemEx(LPITEM item, TItemPos DestCell)   // 5759 lines

The generic hoist refused it, and the refusal was right: the body reassigns
`item` three times (`item = item2;`), so one hoisted value would be stale
afterwards. But three assignments against 113 conversions is worth doing by
hand.

Checked before writing anything:
  * `item` is a by-value LPITEM parameter, not a reference;
  * exactly three assignments, all the plain `item = item2;`;
  * no `&item`, no LPITEM& parameter in the body, no `goto`.

So one MUTABLE entity, refreshed immediately after each assignment, is exactly
equivalent. A redundant inner `entt::entity itemEntity` in a nested block was
folded into it.

The ordering bug this exposed
-----------------------------
The first attempt inserted the three refresh lines and THEN replaced the
conversions. A refresh line is itself spelled

    itemEntity = item ? item->GetEntityHandle() : entt::null;

so the conversion pass matched the refreshes and rewrote them into

    itemEntity = itemEntity;

A no-op. It compiles, links, and silently leaves the entity stale after every
reassignment - the first bug in this whole migration that the compiler would
NOT have caught. It was found by reading the three assignment sites after the
transform rather than trusting the count. The script now does the replacement
first, inserts refreshes second, and asserts that no `itemEntity = itemEntity;`
survives.

Worth generalising: whenever a rewrite inserts text that the same rewrite's
own pattern can match, order matters and an explicit assertion is cheap.

AUDIT - LPENTITY cannot be flipped, and the reason is not size
----------------------------------------------------------------
Asked whether LPENTITY could go to entt::entity at zero conversion cost.
It cannot. Recording the numbers so the question is not reopened.

274 occurrences in 66 files. The usage split looks encouraging at first:

      147  dereferenced (entity->Method(...))
      864  identity only (passed, stored, compared)

and of the 147, 89 are IsType/GetType - type discrimination, which in ECS is
a component check, not a conversion. So on shape alone this axis reads better
than LPCHARACTER did.

The blocker is what the boundary costs. LPCHARACTER->entity is a member read,
`ch->GetEntityHandle()`. LPENTITY->entity is this, in SpatialService.cpp:

    entt::entity EntityFromLPENTITY(LPENTITY entity)
    {
        switch (entity->GetType()) {
        case ENTITY_CHARACTER:  return static_cast<LPCHARACTER>(entity)->GetEntityHandle();
        case ENTITY_ITEM:       ... CItemRegistry::Find(item->GetID())
                                ... then FindByVID(item->GetVID()) as fallback
        case ENTITY_OBJECT:     return CBuildingRegistry::FindByID(...->GetID());
        case ENTITY_NEWSHOPS:   return OfflineShopEntityRegistry::FindByVID(...);
        }
    }

A virtual call plus a hash lookup - two, for items. Only CHARACTER and CItem
carry an m_entity at all; building::CObject and offlineshop::ShopEntity have
no handle member and are reachable only through their side registries. So
writing entt::entity where LPENTITY stands today does not remove conversions:
it removes cheap ones on characters and creates expensive ones everywhere
else. That is the opposite of every phase so far.

And the direction that does pay is already under way from the other end.
entity_view.cpp mirrors every view insert and remove into ViewMap / ViewerMap

Phase 19g - CHARACTER::Damage reads its components directly
------------------------------------------------------------

CORRECTION - every conversion count in this log was measured wrong
--------------------------------------------------------------------
The running "project-wide conversion count" was produced by

    grep -rc "GetEntityHandle() : entt::null" --include=*.cpp ... . |
        awk -F: '{s+=$2} END {print s}'

and that is wrong three separate ways:

  * grep -c counts matching LINES, not matches. A line carrying two
    conversions counted once.                              (undercount, ~113)
  * comments are counted. 141 conversions sit in commented-out debug
    blocks - 26 in CombatSystem.cpp alone, 18 in cmd_gm.cpp, 17 in
    New_PetSystem.cpp.                                      (overcount, 141)
  * the literal string misses conversions spelled with different spacing
    or wrapped across a line.                                (undercount, ~3)

The first two nearly cancel, which is exactly why this survived nineteen
phases without looking wrong.

Measured properly - whitespace-tolerant pattern, comments stripped - the count
at the end of phase 19h is 1694 live sites, not the 1723 reported. Every
absolute number above 19f is off by a similar margin. The DELTAS are sound:
the same wrong method was applied throughout, so the phase-to-phase movement
is real; only the level was misstated.

scratchpad/count_conversions.py is the counter from here on. It reuses the
strip_map from acmd_tool, the same comment-stripping every rewriting tool in
this migration already relied on - the counter was the one place that did not.

That gap is the lesson worth keeping. Every tool that CHANGED code was careful
about comments, because a rewrite inside a comment would have been visible.
The tool that only MEASURED was not, because a wrong measurement looks exactly
like a right one.

Phase 19k - CPIDRegistry, and a wrapper caught before it shipped
------------------------------------------------------------------
FindEntityByPID was itself a round trip:

    {
        LPCHARACTER found = FindByPID(dwPID);

A lookup in the legacy pointer map followed by a conversion off the pointer it

does for VID.

the build did not pick up PIDRegistry.cpp until `cmake -S . -B build` was run
by hand. The symptom is LNK2001 on the new symbol, not a missing-file error.

THE WRAPPER I ALMOST USED
--------------------------
CombatSystem::SetPKMode(entt::entity, uint8_t) exists, and I had already
routed arena.cpp's two SetPKMode calls through it before reading it:

    void SetPKMode(entt::entity e, uint8_t bPKMode)
    {

That is a round trip with a namespace in front of it. Using it would have

Phase 19m - CFSM is gone
--------------------------
CHARACTER no longer inherits from CFSM. FSM.h, FSM.cpp and state.h are deleted;
nothing else in the tree used them.

The machine had exactly two states on CHARACTER, m_stateIdle and m_stateBattle,
and every GotoState call already sat directly beside its ECS twin:

        EnterIdleState(GetEntityHandle());
        if (!IsPC())
            GotoState(m_stateIdle);

The tags were being maintained in lockstep with the FSM the whole time. So the
FSM's own data moves into a component and its two entry points become entity
functions:

    ecs::AIFSMState        Initial / Idle / Battle
    ecs::AIStateMachine    current, pending, hasPending
    AISystem::GotoState(entt::entity, ecs::AIFSMState)
    AISystem::UpdateStateMachine(entt::entity)

GotoState is now entity-native, which is what SetPosition needed. The state
bodies (StateIdle, StateBattle) are still CHARACTER methods, so
UpdateStateMachine resolves the legacy object once per tick at the pump. That
is the boundary the pump already crosses for everything else, not a wrapper
standing between an entity call and a conversion.

FOUR THINGS THAT WOULD HAVE BEEN SILENT
-----------------------------------------
1. CFSM deferred transitions by one Update through m_pNewState. Dispatching
   straight off CombatActiveTag would have made them immediate - a one-tick
   difference in AI behaviour that no build error would show. The component
   keeps current and pending separately.

2. BeginStateEmpty is NOT empty. It logs. CFSM ran it on every transition, so
   UpdateStateMachine calls it when one applies. EndStateEmpty really is empty
   and is dropped.

3. ecs::AIState already existed - a struct holding derived state for network
   sync (currentState, nextStatePulse, stateDuration), a different concern
   entirely. The new enum had to be AIFSMState. The compiler caught this one.

4. There was a SECOND pump. Grepping for "CFSM::Update" found char_manager.cpp
   and CHARACTER::UpdateCharacter, but CHARACTER::UpdateStateMachine called a
   bare `Update()` that resolved through the base class. Removing the base

    SessionSystem             same again
    PlayerRuntimeSystem       CHARACTER::RestartAtSamePos

THIS IS A BUG FIX, NOT ONLY A MIGRATION
-----------------------------------------
entity_view.cpp says, in its own words:

    // For characters, m_map_view is no longer maintained - the legacy
    // CFuncViewInsert polling in UpdateSectree was disabled in D.6

and ValidateViewMapMirror returns early for characters for exactly that
reason. So a character's m_map_view is frozen at whatever it held when D.6
landed. All four of these loops are in CHARACTER methods. They have been
iterating that frozen map: the three overhead updates were notifying a stale
set of viewers, and RestartAtSamePos was resyncing one.

The comments recording that the map was dead for characters were right there
in entity_view.cpp; nothing connected them to the four places still reading it.
That is the failure mode worth naming - a fact was documented at the source and
never propagated to the consumers.

RestartAtSamePos kept both packet directions
----------------------------------------------
It looks like ViewReencode and it is not. ViewReencode dropped the peer
direction in fixup-5 because refreshing peers reset a moving character's
animation; RestartAtSamePos is a deliberate full respawn, so the peer refresh
is its whole purpose. It walks ViewMap now through EntityNetworkDispatch
Send/Remove, but keeps both directions.

Its peer filter was preserved rather than simplified. The original let every
non-character through and filtered characters to IsPC() || IsNPC() ||
IsMonster() - which, since IsPC() is the descriptor test and IsNPC() is
m_bCharType != CHAR_TYPE_PC, excludes exactly one thing: a CHAR_TYPE_PC entity
with no descriptor, a link-dead player. The rewrite tests SpatialKindTag for
character-ness and then reproduces that condition, rather than collapsing it
to "always true", which is what it looks like at a glance.

m_map_view now has readers only inside entity_view.cpp: ViewCleanup,
ViewReencode's non-character branch, ViewInsert, ViewRemove and UpdateSectree.
Those are the last ones before the member, the MirrorView* functions and
ValidateViewMapMirror can go.

Phase 19q - m_map_view is deleted
-----------------------------------
CEntity::m_map_view and the ENTITY_MAP typedef are gone. ViewInsert and
ViewRemove write ecs::ViewMap directly; the ECS view is the view, not a mirror
of a legacy structure.

This is the "Phase G" the file kept referring to. UpdateSectree said it in so
many words:

    // m_map_view, m_iViewAge, and the ValidateViewMapMirror audit are all
    // unmaintained for characters until Phase G deletes them outright.

What went with it:
  * MirrorViewInsert / MirrorViewRemove - ViewInsert and ViewRemove ARE those
    functions now, plus the presence test m_map_view used to answer
  * ValidateViewMapMirror, 80 lines - it compared two structures and there is
    one left, so there is nothing to drift
  * FuncPacketView in entity.cpp - defined, never instantiated; PacketView has
    walked ViewerMap since D.8

The three UpdateSectree stale sweeps and the ViewCleanup / ViewReencode
non-character walks read SnapshotView(), which takes the (peer, age) pairs out
of ViewMap + ViewAgeMap. They still yield LPENTITYs, because the loop bodies
call CEntity::ViewRemove and the LPENTITY dispatchers - that is honest and it
is written down at the helper. What moved is the AUTHORITY: nothing reads a
legacy container to decide what an entity can see any more.

THE ORDERING THAT WOULD HAVE BROKEN IT
----------------------------------------
Doing only what was asked - pointing ViewInsert and ViewRemove at ViewMap -
would have left UpdateSectree's three stale sweeps iterating an m_map_view that
nothing filled any more. Items, buildings and offline shops are the only
entities that still run that polling, and their stale-view cleanup would have
silently stopped: no crash, no warning, just peers never being removed from
each other's view. The whole set had to move together or not at all.

One deliberate behaviour change, logged rather than hidden: ViewInsert now
returns early with [VIEW_UNTRACKED] if either side has no ECS handle, where
before it would have tracked the pair in m_map_view. Every entity that reaches
ViewInsert is an item, building or offline shop, and all three are registered
in their own ECS registry, so this should never fire - which is exactly why it
logs instead of failing quietly.

Phase 19r - packet parity: a real gap, and an audit that could not see it
--------------------------------------------------------------------------
SendInsert's character case still calls legacy EncodeInsertPacket. The plan
was to flip it to the native builder. Reading the two side by side first found
a reason not to, yet.

THE GAP
--------
Legacy CHARACTER::EncodeInsertPacket opens with

    ch->SendGuildName(GetGuild());

telling the VIEWER the name of the SOURCE's guild, deduplicated per viewer.
SendCharacterInsert, the native path, never did. Flipping authority would have
meant viewers stop learning guild names and characters render without one -
a visible bug, shipped on the strength of a green audit.

CheckCharacterInsertParity could not have caught it. It compares fields of
TPacketGCCharacterAdd; SendGuildName is a different packet entirely. An audit
scoped to one struct cannot see a missing sibling.

Closed by moving the send: ecs::SocialSystem::SendGuildName(viewer, guild) is
the implementation now, CHARACTER::SendGuildName forwards, and the dedup set
m_known_guild is an ecs::KnownGuilds component. SendCharacterInsert calls it.

WHAT ELSE THE AUDIT WAS NOT TELLING US
----------------------------------------
Three of its nine comparisons cannot fail. GetRotation, GetAddChrStateFlag and
GetCurrentDestX/Y are already component-backed, so those lines compare a
component with itself. Kept - they mean something again the moment either side
moves - but annotated, because "the parity audit is clean" was resting partly
on lines that are clean by construction.

Four packet fields were never compared at all: dwAffectFlag[0], dwAffectFlag[1],
bMovingSpeed and transname. dwAffectFlag now is. It is the one where the two
builders genuinely do independent work - both apply the SOUL_RED + SOUL_BLUE
-> SOUL_MIX collapse, from different sources - so it is worth watching.

bMovingSpeed and transname are left uncompared and it is worth saying why:
both branch on a pet/mount/special-race test that the two builders spell
differently. Legacy reads IsPet() / IsNewPet() / m_bIsMount; native reads
StatusFlags isPet / isNewPet / isMount. Comparing the outputs would tell us
they agree today without telling us the inputs are two separate stores. That
needs the flags consolidated, not a log line.

CheckMovementDrift is deleted. It had been an empty no-op shim since C.4, with
a comment saying the shim and its call site delete in Phase G. This is Phase G.

AUTHORITY NOT FLIPPED, DELIBERATELY
-------------------------------------
The native builder is not authoritative for character inserts yet, and this
phase is the argument for why not. Reading two builders against each other
found a gap in minutes that the automated check was structurally incapable of
reporting. The remaining evidence - a partly tautological field audit that only
runs under AURIGA_LPENTITY_FIXUP_AUDIT and only logs - is not enough to move
every character-insert packet on a live server. What would be: the widened
audit running on a populated server with no [INSERT_PARITY] output, plus
bMovingSpeed's inputs unified.

Phase 19s - the pet/mount flags meant two different things
------------------------------------------------------------
19r left bMovingSpeed and transname uncompared because the two packet builders
read the pet/mount test from different stores. Unifying them turned up why
that mattered.

    legacy   m_bIsMount, set by CHARACTER::SetMount()
             called from CMountActor::Summon on m_pkChar - the SUMMONED MOUNT
             "this character IS a mount"

    ECS      StatusFlags::isMount, set in questlua_pc pc_mount
             on the PC doing the mounting - the RIDER
             "this player IS RIDING"

Opposite subjects, same name, and the native character-insert builder reads the
ECS one as though it meant the legacy one. A riding player would have been
packed as a mount: transname false instead of true, and the mount branch of
bMovingSpeed. Multi-language names would have broken for every mounted player
the moment packet authority moved.

isPet and isNewPet were worse in a quieter way: no ECS writer at all. Legacy
PetSystem and New_PetSystem call SetPet()/SetNewPet() on the creature, nothing
ever set the StatusFlags bits, so the native builder's pet detection was dead
code that always evaluated false.

And isMountActive - the bit whose name actually describes the rider state - had
no readers. Written twice in questlua_pc, read nowhere.

WHAT CHANGED
-------------
  * StatusFlags now says which bits belong to the creature and which to the
    rider, at the declaration.
  * SetPet / SetMount / SetNewPet stop being inline one-liners and write both
    stores from one place, so they cannot drift.
  * pc_mount writes isMountActive only, and pc_is_mount reads it. The rider
    state uses the bit named for it; isMount goes back to meaning the creature.

MY FIRST READING OF THIS WAS WRONG
------------------------------------
Worth recording. The first grep - for `SetPet()|SetMount()|->SetPet` and so on -
came back with nothing but declarations, and the conclusion drawn from it was
that all three legacy flags were dead and always false. They are not: the calls
are `m_pkChar->SetMount();` inside the pet and mount actors, which the pattern
missed. A wider grep found them.

Had that first reading been acted on, the "fix" would have deleted three live
flags. The lesson is narrow and practical: when a grep says a thing is dead,
widen the pattern before believing it - absence of evidence from one regex is
not evidence of absence.

bMovingSpeed and transname can be added to CheckCharacterInsertParity now that
both builders read the same store, but they should be added by whoever can run
the audit on a populated server, together with the rest of the parity evidence.

Phase 19t - bMovingSpeed and transname, and two more of the same trap
-----------------------------------------------------------------------
Both fields are compared in CheckCharacterInsertParity now. With the creature
flags unified in 19s the comparison finally measures the builders rather than
the confusion between the two flag stores.

Adding it meant reading the two branches against each other line by line, and
that turned up two more divergences - both the SAME predicate trap that has now
appeared five times in this migration:

    CHARACTER::IsPC()               GetDesc() != nullptr   a client is attached
    ecs::PlayerRuntime::IsPC(e)     TagPC component        spawned as a PC

  1. LimitedPoint caps POINT_ATT_SPEED at 170 for a PC and 250 otherwise, and
     was asking TagPC. CHARACTER::GetLimitPoint asks IsPC(). A link-dead
     player - TagPC set, descriptor gone - was capped at 170 natively and 250
     legacily. bAttackSpeed IS in the audit, so this one would eventually have
     been caught by a running server; it was caught by reading instead.

  2. BuildCharacterInsert's bMovingSpeed ternary had it too, in the branch the
     audit did not cover. That one would not have been caught at all.

Both now use GetDesc(). This is the fifth occurrence - SetPosition,
StartRecoveryEvent, MonsterLog, IsGuardNPC and now these two - and the pattern
is worth stating once more: the legacy predicates were named before the
components existed, and every ECS function with a matching name means something
narrower. IsPC, IsNPC, IsMount: all three have this problem.

One thing checked and cleared: LimitedPoint reads ecs::PointSystem::Get while
GetLimitPoint reads m_pointsInstant.points directly. Not a divergence -
PointRouter maps every type to SRC_INSTANT_ARRAY by default and neither
MOV_SPEED nor ATT_SPEED overrides it, so both read the same array.

Every field of TPacketGCCharacterAdd that either builder writes is compared
now. What is still missing to flip authority is not more code: it is the audit
running on a populated server with no [INSERT_PARITY] output. That needs a
server, which this seat does not have.
