Infrastructure conclusions:
- EVENTFUNC is defined in `SRC/Server/GameServer/event.h` as `#define EVENTFUNC(name) int32_t (name) (LPEVENT event, int32_t processing_time)`.
- event_create is exposed via `event_create` macro -> `event_create_ex` in `event.h`, implemented in `SRC/Server/GameServer/event.cpp`.
- event_cancel is declared in `event.h` and implemented in `event.cpp`.
- Central event queue ownership lives in `event_queue.h` / `event_queue.cpp` and the static queue instance `cxx_q` inside `event.cpp`.
- Central event loop / dispatcher is `event_process(int pulse)` in `event.cpp`, driven from `heartbeat()` in `main.cpp` before `CHARACTER_MANAGER::Update()`.
- `thecore` / `common` do not appear to own a second server-side EVENTFUNC implementation; the active timed-event runtime is the GameServer `event.*` stack.

Step 11 - Auditor conclusions
=============================
- The legacy timed event runtime is still heavily centered on `LPEVENT` handles stored directly on `CHARACTER` and other gameplay objects.
- The highest-friction migration areas are combat/skill/session events because they call CHARACTER methods or write CHARACTER-owned state directly.
- Best Phase 10 entry points are the NO_LEGACY and selected READS_ONLY candidates listed above, especially self-contained world / dungeon / timer events that do not mutate CHARACTER state directly.
- ECS dispatcher support exists, but it is currently event-trigger oriented and not yet a replacement scheduler for the legacy `event_process()` queue.
