## First Target Recommendation
**Best first target: extract the `m_pointsInstant` blob (and then the adjacent `m_points` base block) into ECS-owned runtime point/inventory components.**

Why this wins first:
- `m_pointsInstant` alone is roughly **34,335 bytes** per CHARACTER, dwarfing every other single member.
- `m_points` adds another **2,092 bytes** right next to it, so the combined points/runtime cluster is about **36,427 bytes** per CHARACTER.
- This cluster is also on hot paths: movement, combat stats, inventory/equipment, quickslots, DragonSoul, cube/refine windows, and transient runtime flags all read it constantly.
- Pulling this blob out is the clearest path to shrinking `sizeof(CHARACTER)` meaningfully and reducing the amount of state that forces `LegacyCharOf(e)` back-bridges.

Proposed component split:
- `CharacterPointsBaseComponent`: current `m_points` payload (`points[]`, level/exp/gold/gaya/hp/sp/stamina/job/skill_group`).
- `CharacterRuntimePointsComponent`: current `m_pointsInstant.points[]`, max HP/SP/Stamina, rotation, position, instant flags, AI/immune flags, parts, base part, deck state.
- `InventoryRuntimeComponent`: `pItems`, `bItemGrid`, `pDSItems`, `wDSItemGrid`, extra inventory arrays, switchbot/cube/acce/attr-transfer window pointers.
- `InteractionWindowComponent`: transient NPC / refine / cube / attr-transfer / DragonSoul opener pointers that are currently embedded in `m_pointsInstant`.

Estimated savings if the first target is completed:
- Per CHARACTER: about **36,427 bytes** (~35.6 KiB).
- At 1,000 online characters: about **34.7 MiB** reclaimed from live CHARACTER objects.

Suggested migration steps:
- Introduce mirror ECS components for `m_points` and `m_pointsInstant` without deleting the CHARACTER fields yet.
- Populate them on character creation/login and keep them synchronized from the existing authoritative write paths.
- Move read-mostly accessor sites (`GetLevel`, `GetPoint`, `GetPart`, `GetRotation`, inventory slot readers) to ECS-backed accessors first.
- Flip hot runtime systems (Combat, Movement, Item, Mount, Skill) to read from the new components directly.
- Move window/inventory transient pointer surfaces behind small bridge helpers so `CHARACTER` no longer owns the arrays.
- After callers are drained, remove `m_pointsInstant` from `CHARACTER`, then remove `m_points` in a second cut.
- Finally add an exact compiler `sizeof(CHARACTER)` check once the field removals land.

Main blockers / risks:
- `m_pointsInstant` is a mixed mega-blob: runtime stats, inventory pointers, window state, and combat-adjacent state are packed together. It should be split, not migrated as one opaque struct.
- Inventory authority still lives on `CHARACTER::m_pointsInstant.pItems`; moving it requires careful sync with ItemSystem and every inventory window path.
- Many write paths are hot and implicit (`PointChange`, equip/unequip, DragonSoul, cube, refine, stat recompute). Mirroring first is safer than direct authority transfer.
- Exact byte savings will differ slightly from this audit because compiler padding and feature-flag combinations can change the real layout.

## Next 5 Targets (Roadmap)
1. `G_POINTS` ? Biggest size win by far and central to hot-path reads; it also unlocks later bridge elimination.
2. `G_EVENT_HANDLES` ? Small, self-contained pointer cluster with almost no data coupling; easy early shrink after points mirroring starts.
3. `G_IDENTITY` ? Mostly scalar data with good ECS coverage already present; cheap cleanup after the large runtime blobs move out.
4. `G_POSITION` ? Already partially ECS-backed; finishing the mirror removes constant `CHARACTER` position/rotation reads from movement/combat code.
5. `G_VITALS` ? Follow the byte/frequency ranking.
6. `G_SOCIAL` ? Party/guild/shop/safebox pointers are numerous but less frame-hot than points/combat.

## Estimated Size After Top 5 Migrations
- Current rough size: ~38,620 bytes.
- If the top 5 ranked groups move fully out of `CHARACTER`: ~1,435 bytes remain in the shell object.
- In practice the first two migrations will dominate; later cuts are more about bridge elimination than raw bytes.
