# C37 — Independent Nexoria item windows

The native-item UI now opens separate, compact windows instead of the previous large item-management dashboard. Windows can remain open together; desktop users can drag their headers, focus a window and close it independently. Escape closes the front window. The inventory has independent details, wardrobe, rune, companion and combat-stat views. The system menu follows the supplied vertical menu layout. Storage has an item grid and paging rather than visible administrative route/command tabs.

Source branches: server Git `20261103`; Unity Version Control `/main/unity63-integration-20261103`, pinned Editor `6000.3.27f1`. Unity source is checked in as changeset **98** (328 reviewed source/artwork paths). The paired Git work on `20261103` contains this report, evidence and the PSD exporter; native server code is unchanged from the C36 baseline.

## Artwork and input

The continued Photoshop window kit is the `nx_window_kit.jsx` / `nx_export_unity_window_kit.jsx` kit from `D:/Nexoria UI/Unity_Export/scripts`. The HUD now uses the supplied `D:/Nexoria UI/Taskbar/Nexoria_Taskbar.psd`, including five exported layers/composites for the hero frame, portrait, lower band, hotbar frame and navigation background. Export provenance, layer bounds and output hashes are in Unity's `Resources/Metin2/NexoriaUI/taskbar-source.json`. `tools/ui/ExportNexoriaTaskbar.py` reproduces those composites while preserving existing Unity GUIDs and refusing unrecorded output edits. The static portrait's level badge is excluded; level, name, HP/SP, XP and wallet values are runtime data.

The HUD retains eight real native-item hotbar slots and the nine supplied navigation actions. Storage, recovery, effects and polymorph utilities have separate entry points. Existing touch movement/skill controls remain connected. The layout accounts for safe areas and portrait scrolling, with a pinned close control and a physical minimum font size.

Closing an item window hides that window immediately. Its original protocol cancellation runs after an outstanding authoritative operation completes. Late snapshots cannot reopen a dismissed window; an explicit user open clears dismissal. A trade already committing is treated as busy. Each operation owner exposes its own Canvas; the layout resolves pending state against that Canvas because all production window controllers share one bootstrap object. Regression checks cover both a pending shop beside an idle owner and an idle shop beside another busy owner. Shared controls raise the close hit target after dynamic content refreshes, preventing later UI elements from covering X.

There are no native C++ changes, new packet layouts, schema changes or legacy-item conversions in C37. The storage grid preserves server instance IDs, footprint, cell positions, preview/confirmation and wallet authorization. The server continues to be authoritative. The existing storage protocol has one active route per character; selecting a storage type opens that route in its titled storage window.
